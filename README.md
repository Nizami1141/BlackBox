# Пограничный пост: лицо сотрудника + штрихкод груза

> По умолчанию снова выбран общий вариант на одной ESP32-S3: камера,
> W5500, GM67, LCD и кнопка. Вариант на двух платах сохранён отдельно:
> [docs/TWO_BOARD_ESP_NOW.md](docs/TWO_BOARD_ESP_NOW.md).

Единый проект. Собран из двух половин, которые до этого жили порознь:
рабочее демо `esp32cam-ble-demo` (камера и сканер по Bluetooth — оно
работало) и сервер `customs-checkpoint` (распознавание, база, журнал —
он был написан под Wi-Fi, которого на месте нет).

Что получилось: **один процесс на ноутбуке** поднимает сайт, API и мост до
платы. Оператор открывает страницу, нажимает кнопку — плата снимает кадр,
сервер ищет лицо в базе, и только после опознания включается сканер
штрихкодов. Результат ложится в журнал строкой «такого-то числа такой-то
сотрудник проверил такой-то груз».

---

## Что изменилось по сравнению с двумя старыми папками

| Было | Стало | Почему |
|---|---|---|
| Сервер ждал `POST /verify` от платы по Wi-Fi | Сервер сам командует платой через транспортный слой | Инициатива у кнопки на сайте, а не у платы |
| BLE-клиент — отдельная программа на PyQt | BLE-мост внутри сервера | Bluetooth-адаптер Windows отдаёт устройство только одному процессу |
| Интерфейс — окно PyQt | Сайт на `http://127.0.0.1:8000/` | Просили сайт; и открыть его можно с любого экрана |
| GM67 в Continuous — светит всегда | GM67 в Host Mode — светит после опознания | Иначе груз можно отметить без сотрудника |
| Фото каждые 5 секунд | Кадр по команде `VERIFY` | Сервер не должен получать лица, которых никто не просил |
| Порог 0.42, бэкенд OpenCV/SFace 128-d | Порог 0.45, бэкенд InsightFace **buffalo_l** 512-d | Всё локально, точность заметно выше |

Прошивка изменилась минимально — три файла, разбор в `docs/FIRMWARE_CHANGES.md`.
Протокол BLE-пакетов не тронут вообще, поэтому старое демо продолжает работать.

## Как это работает

```
   [ Сотрудник ]
        │  смотрит в камеру
        ▼
┌────────────────────┐   Ethernet, W5500 (сейчас)   ┌──────────────────────────┐
│   ESP32-S3 WROOM   │◀────────────────────────────▶│   Ноутбук: один процесс  │
│                    │      BLE (стенд, запасной)   │                          │
│  OV5640  камера    │                              │  сайт  +  API  +  мост   │
│  GM67    сканер    │                              │                          │
└────────────────────┘                              │  buffalo_l → вектор 512d │
                                                    │  косинусный поиск        │
   плата не считает эмбеддинги                      │  SQLite: база + журнал   │
   и не хранит базу — она тонкий клиент             └──────────────────────────┘
```

Один проход проверки — **Ethernet, рабочий режим**:

```
1.  сотрудник жмёт кнопку на самом посту
2.  плата будит камеру и снимает JPEG
3.  POST /api/recognize — JPEG как multipart/form-data, заголовок X-API-Key
4.  сервер: детекция лица → выравнивание → эмбеддинг → поиск по базе
5а. не нашли  → «Giriş qadağandır» на экране, сканер даже не включался
5б. нашли     → выдан log_id (внутри связан с одноразовой сессией на 90 с)
6.  плата зажигает луч            ← только здесь, и только получив токен
7.  сотрудник подносит штрихкод груза
8.  POST /api/log_cargo — log_id + код; сервер проверяет сессию и пишет в журнал
9.  «Yük qeyd edildi» на экране, луч погашен, сканер усыплён
```

Шаг 6 — единственное место, где включается сканер, и он идёт строго после
шага 5б. Но настоящая гарантия не в этом, а в шаге 8: **луч плата зажечь
может когда угодно, а токен — нет**. Токен выдаёт только сервер и только
после успешного опознания, и без действующего токена запись в журнал не
появится, чем бы плата ни светила. Тест
`tests/test_flow.py::test_unknown_face_never_enables_scanner` проверяет
первую половину, `tests/test_device_api.py` — вторую.

В стендовом режиме (BLE) те же девять шагов идут в другую сторону:
начинает оператор кнопкой «Проверить» на сайте, а команды `VERIFY`,
`SCAN ON`, `SCAN OFF` шлёт плате сервер. Решения в обоих случаях
принимает сервер — у платы нет ни базы, ни модели.

## Запуск

### 1. Сервер

```powershell
cd server
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python -m tools.download_models      # ~300 МБ buffalo_l, один раз
python app.py --open
```

Откроется `http://127.0.0.1:8000/`.

Проверить настройки, ничего не поднимая: `python app.py --check`

### 2. Плата

```powershell
cd firmware
pio run -e esp32s3cam -t upload --upload-port COM9
pio device monitor -e esp32s3cam -p COM9 -b 115200 --rts 0 --dtr 0
```

Если CH343 получил другой COM-порт, замените `COM9` в обеих командах.
Для этого общего варианта вход с сайта не запускает проверку: `GATE-01`
настроен как автономный Ethernet-пост, проверка начинается нажатием
физической кнопки на плате. `SIM-01` на сайте — отдельная заглушка.

В логе должно быть:

```
=== Пост "GATE-01": автономный режим, связь по Ethernet ===
[boot] сканер ответил на команды — связь по UART в обе стороны есть
[eth]  поднимаю W5500 (SCK=39 MISO=40 MOSI=38 CS=41 RST=42)...
[eth]  статический адрес 172.16.6.52
[cp]   сервер отвечает: сотрудников в базе: 3, модель insightface
```

Строка `[cp] сервер отвечает` — та, ради которой стоит смотреть лог: она
означает, что дошло всё, от кабеля до ключа устройства.

Адрес `172.16.6.52` должен быть связан с `GATE-01` в
`server/config.yaml → aks_api.ip_devices`, а `ETH_API_KEY` должен совпадать
с `aks_api.api_key`. Иначе сервер вернёт 401 (ключ) или 403 (IP).

### 3. Порядок действий на демонстрации

1. Открыть `/enroll`, включить веб-камеру, снять 3–5 кадров, сохранить сотрудника.
2. Встать перед камерой поста и нажать **кнопку «ПРОВЕРИТЬ» на сайте**
   либо физическую кнопку на плате.
   На экране 1602 пойдёт «Kameraya baxın» → «Yoxlanılır...».
3. После фамилии появится «Kodu skan edin» — вот здесь загорается луч.
   Поднести штрихкод груза.
4. «Yük qeyd edildi» на экране — записано.
5. Открыть `/journal` — там появилась строка.

Для GATE-01 кнопка на сайте включается после того, как плата с новой
прошивкой начала опрашивать сервер по Ethernet. Сайт ставит разовую команду,
плата забирает её и запускает тот же сценарий, что физическая кнопка.
Для проверки интерфейса без платы остаётся пост-заглушка `SIM-01` — см.
«Без платы» ниже.

## Без платы

В `config.yaml` есть второй пост `SIM-01` с `link: {type: fake}`. Он
проигрывает весь сценарий целиком: отдаёт картинки из `server/data/fake_faces`
и «читает» штрихкод через 2 секунды. Положите туда несколько JPEG с лицами —
и сайт можно показывать, не подключая ничего.

## Регистрация сотрудников

Страница `/enroll`: веб-камера браузера или загрузка файлов. Каждый снимок
сразу проверяется сервером — сколько лиц видит детектор и не слишком ли они
мелкие. Оператор узнаёт о негодном кадре в момент съёмки, а не при сохранении.

Эталон = усреднённый нормализованный вектор по всем снимкам. Считается тем же
пайплайном, каким потом идёт опознание, поэтому «зарегистрировали одним,
ищем другим» невозможно.

**Важно про веб-камеру.** Эталон снят одной камерой, а опознание идёт кадром
с OV5640 — разная оптика, баланс белого и шум. Схожесть у одного и того же
человека при этом падает примерно на 0.03–0.07. Если пойдут ложные отказы,
не опускайте порог вслепую: добавьте сотруднику 2–3 кадра уже с поста
(кнопка «Добавить снимки»). Это честнее, чем ослаблять порог для всех.

## Автономный пост: кнопка, экран, Ethernet

**Рабочий режим системы.** Bluetooth убран полностью: на границе он не
работает, как и Wi-Fi. Пост стоит сам по себе — сотрудник нажимает кнопку
у камеры, читает вердикт на экране 1602, а плата разговаривает с сервером
по кабелю через W5500.

```
   нажал кнопку
        │
        ▼
   камера просыпается (была выключена — не грелась)
        │
        ▼
   кадр уходит серверу
        │
        ├── не узнали → экран: «Giriş qadağandır»,  сканер НЕ включался
        │
        └── узнали    → экран: фамилия
                        экран: «Kodu skan edin»   ← вот эта просьба
                        луч сканера загорается
                              │
                              ▼
                        поднесли штрихкод
                              │
                              ▼
                        экран: «Yük qeyd edildi», запись в журнале
```

Пост — HTTP-клиент: он опрашивает сервер за командами и сам отправляет кадр
и штрихкод. Но решения
по-прежнему принимает сервер — у платы нет ни базы, ни модели, и запись
в журнал сервер делает только по одноразовому токену, который выдаётся
исключительно после успешного опознания. Подменённая прошивка может
зажечь луч когда угодно, но токена у неё не будет.

Кнопка «Проверить» на сайте доступна, пока сервер видит регулярные опросы
автономного поста. При потере Ethernet она выключается.

Стендовый режим с Bluetooth никуда не делся — `ENABLE_BLE 1` вместо
`ENABLE_ETH 1` в `config.h`, и всё возвращается к работе с ноутбуком рядом.
Одновременно включить нельзя: сборка остановится с сообщением.

Тексты для экрана лежат в `server/config.yaml`, секция `lcd:` — поправить
формулировку на азербайджанском можно, не перепрошивая посты. Плата
переводит UTF-8 в знакоместа HD44780 сама: букв ə ı ö ü ç ş ğ в
знакогенераторе нет, они рисуются программируемыми знакоместами CGRAM.

**Пошаговый запуск Ethernet с нуля — `docs/ETHERNET_BRINGUP.md`.
Подключение и распиновка — `docs/WIRING_V2.md`.
Настройка Ethernet-режима, питание и разбор нагрева — `docs/ETHERNET_MODE.md`.**

### Управление нагревом камеры

OV5640 не имеет своего генератора — его тактирует ESP32 сигналом XCLK.
Пока клок идёт, внутри сенсора работает всё: ФАПЧ, дерево тактирования,
аналоговая часть, кодировщик JPEG. И он снимает кадры непрерывно, около
тридцати в секунду, независимо от того, забирает их кто-нибудь или нет.

На посту из этих тридцати кадров в секунду используется один раз в
несколько минут. Остальное греет коробку.

**Три состояния** (`CAM_POWER_PLAN` в `config.h`, реализация в `src/camera.*`):

| Состояние | Что происходит | Пробуждение |
|---|---|---|
| `ACTIVE` | снимаем | — |
| `STANDBY` | сенсор в программном сне (регистр 0x3008), XCLK снят, драйвер жив | ~180 мс |
| `OFF` | драйвер остановлен целиком | ~1.1 с |

Обычный покой — `STANDBY`. Полное выключение наступает после
`CAM_DEEP_OFF_MS` простоя (по умолчанию две минуты).

Почему `STANDBY` лучше полной остановки для обычной работы: при остановке
драйвера сенсор теряет все регистры и после включения сходится по
экспозиции с заводских значений — отсюда 350 мс ожидания и два выброшенных
кадра. В режиме сна регистры остаются, автоматика уже настроена на здешний
свет, хватает 120 мс и одного кадра. Пост отвечает вдвое быстрее и греется
меньше, потому что меньше времени проводит включённым.

**Дополнительно:**

- `CAM_XCLK_HZ` снижен с 20 до 10 МГц — примерно вдвое меньше потребления
  дерева тактирования и во время самой съёмки. Ниже 8 МГц опускать нельзя:
  внутренняя ФАПЧ перестаёт надёжно захватывать частоту.
- `CAM_FB_COUNT` 1 вместо 2. Двойная буферизация нужна видеопотоку; здесь
  второй буфер означал лишний отснятый кадр на каждую проверку.
- `CAM_MIN_INTERVAL_MS` — минимальная пауза между съёмками, чтобы частым
  нажатием кнопки нельзя было держать камеру включённой постоянно.

**Тонкость с частотой процессора.** XCLK формирует блок LEDC, а его делитель
считается от шины APB, которая меняется вместе с частотой процессора. Просто
возобновить остановленный таймер после перехода с 80 на 240 МГц нельзя —
XCLK окажется втрое выше положенного. Поэтому при каждом пробуждении частота
XCLK задаётся заново (`ledc_set_freq`), и результат не зависит от того, на
какой частоте сейчас процессор.

**Как убедиться, что работает.** Раз в десять секунд в лог идёт строка:

```
[cam] лёгкий сон | снимков: 4 | камера работала: 3 с | кристалл: 41.2 C
```

Смотреть надо не на абсолютную температуру (датчик грубый), а на две вещи:
растёт ли она со временем и сколько секунд камера в сумме была включена.
При десяти проверках за час «камера работала» должно быть порядка трёх-пяти
секунд, а не часа.

## Если что-то не работает

### Интерфейс зависает при добавлении сотрудника

Исправлено. Причина была в `core/face_engine.py`: страница регистрации
проверяет каждый снимок сразу после съёмки, оператор снимает их подряд,
и к модели приходило несколько обращений одновременно. Ни один из бэкендов
к этому не готов — у OpenCV детектор хранит размер входа внутри объекта,
у InsightFace сессия переиспользует внутренние буферы. Теперь все обращения
к моделям идут через один замок.

### После перезапуска сервер не поднимается

Смотрите, что он печатает. Если что-то про размерности векторов:

```powershell
python -m tools.db_doctor
```

Так бывает после смены `face.backend`. У `insightface` вектор 512-мерный,
у `opencv` — 128-мерный, и старые записи остаются в базе с прежней длиной.
Раньше это роняло сервер прямо в конструкторе; теперь несовместимые записи
исключаются из поиска, а `db_doctor` показывает их и умеет удалить
(`--purge`). Записи в журнале при этом сохраняются.

### Распознавание работает медленно

Три ручки в `config.yaml`, в порядке эффективности:

```yaml
face:
  det_size: 320      # было 640 «как в примерах» — вчетверо дороже
  max_side: 800      # снимки веб-камеры 1280x960 ужимаются перед моделью
  threads: 4         # если сервер мешает остальной работе ноутбука
```

`det_size: 320` — главное. На посту лицо занимает половину кадра, и большего
разрешения детектору не нужно. Сколько времени уходит на каждый этап, видно
в `/api/web/state` в поле `last_face_ms`, а при `logging.level: DEBUG` —
в логе построчно.

Если и этого мало — переключитесь на `backend: "opencv"`. Он заметно быстрее
и легче, ценой точности; для показа концепта разницы не увидите.

### Сразу после опознания приходит штрихкод из одного символа

Исправлено, но лечится в двух местах, и оба нужны.

Причина: в Host Mode сканер отвечает подтверждением на каждую команду —
кадром `04 D0 04 00 FF 28`. Раньше `flushInput()` вызывался *до* отправки
`START_DECODE`, а ответ приходил *после* и оставался в буфере. Дальше
`poll()` пропускал эти байты через фильтр «оставляем только печатный ASCII»:
`04 D0 04 00 FF` отбрасывались, а `0x28` — это символ `(` — оставался.
Через 60 мс паузы одиночный символ уезжал наружу как прочитанный штрихкод.
У других команд контрольная сумма другая, поэтому мусор бывал и `$`.

Что сделано:

* **Прошивка** (`gm67.cpp`): после `START_DECODE`/`STOP_DECODE` служебный
  ответ вычитывается и выбрасывается; строки короче `GM67_MIN_CODE_LEN`
  (4 символа) и всё, что пришло в первые `GM67_GUARD_MS` (150 мс) после
  включения луча, не считаются кодом.
* **Сервер** (`core/flow.py`): обрывки короче `flow.min_barcode_len`
  отбрасываются, ожидание продолжается. Сервер не полагается на то, что
  на посту стоит свежая прошивка: записать в журнал груз с номером `$`
  гораздо хуже, чем подождать ещё немного.

**Прошивку надо перезалить** — без этого сервер отбросит мусор, но плата
продолжит его слать.

## Что ещё не сделано

Это честный список, а не формальность — по каждому пункту система работает,
но в эксплуатацию в таком виде идти нельзя.

1. **Liveness не реализован.** Систему проходит распечатанная фотография.
   Заглушка в `core/liveness.py`, план в `docs/ARCHITECTURE.md` §3.2.
   Это блокер номер один.
2. **Порог не откалиброван** на реальной базе. Есть
   `tools/calibrate_threshold.py`, но пока в базе меньше десятка человек,
   считать нечего.
3. **HTTP, а не HTTPS.** Ключ устройства ходит открытым текстом. Для локальной
   сети поста терпимо, для реальной эксплуатации нужен wss + клиентские
   сертификаты.
4. **Автофокус OV5640 не управляется** драйвером esp32-camera — нужен блоб
   прошивки AF. Пока фокус фиксированный, и это влияет на резкость лица.
5. **Регламент по биометрическим ПДн** не написан: сроки хранения векторов,
   удаление при увольнении, кто имеет доступ к журналу.

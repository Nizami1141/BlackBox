# ESP32 в общей сети: прямой доступ к AKS

## Сетевые настройки

| Параметр | Значение |
|---|---|
| Баку — IP / маска / шлюз | `172.16.5.193` / `255.255.0.0` / `172.16.0.1` |
| Товуз — IP / маска / шлюз | `172.20.204.193` / `255.255.255.0` / `172.20.204.1` |
| AKS | `aks.customs.gov.az`, HTTPS-порт `443` |
| API | `https://aks.customs.gov.az/api` |
| Общий DNS | `192.168.250.248` (`ETH_DNS`) |
| Ethernet MAC W5500 | `02:47:41:54:45:01` |

Сетевые параметры обновлены 23.10.2026 и находятся в `firmware/include/config.h`.
`ETH_DIRECT_AKS=1`, `ETH_USE_STATIC=1`.
По умолчанию — `esp32s3cam_baku`; для поля — `esp32s3cam_tovuz`.
Выбор профиля и команды: [SITE_NETWORKS.md](SITE_NETWORKS.md).

Адрес сервера обновлён по приложенному контракту от 30.09.2026.
Для Arduino Ethernet 2.0.2 TLS реализован через ESP_SSLClient 3.1.3:
обычный EthernetClient сам по себе не умеет HTTPS. Домен используется
и в HTTP Host, и в TLS SNI. Wi-Fi для этого не включается.
Основа реализации: [пример ESP32 + W5500 автора ESP_SSLClient](https://github.com/mobizt/ESP_SSLClient/blob/main/examples/Ethernet/Ethernet.ino).

`ETH_DNS` задаётся отдельно от шлюза: `192.168.250.248` для обеих площадок.
DNS доступен через шлюз выбранного профиля. В сети должен быть разрешён
DNS-трафик к этому адресу. Резервные DNS по умолчанию не заданы.
Произвольный публичный DNS может не знать
внутренний адрес AKS. Статический IP платы и разрешение по IP не заменяют DNS.

Для первичного подключения выбран режим документа `ETH_TLS_INSECURE=1`:
трафик шифруется, но сертификат сервера не проверяется. Для проверки
подлинности сервера задайте `ETH_TLS_INSECURE=0` и `ETH_TLS_FINGERPRINT`
(SHA-1 fingerprint сертификата, полученный от администратора по доверенному
каналу); при обновлении сертификата этот fingerprint нужно обновить.

Предыдущая ошибка с `172.16.6.51:8000` означала попытку найти сервер на
ноутбуке. Теперь W5500 подключён к общей сети; в ней назначения
`172.16.6.51:8000` и шлюз `172.16.6.51` не соответствовали нужной схеме.

Для выхода к AKS в Баку используется маршрутизатор `172.16.0.1` в подсети
`172.16.0.0/16`, в Товузе — `172.20.204.1` в `172.20.204.0/24`.
В каждом случае IP платы и шлюз находятся в одной подсети. Если администратор
меняет VLAN/маску поста, надо пересогласовать IP и шлюз вместе.

## Сценарий

Плата не загружает базу лиц и не распознаёт лица сама. По контракту
[esp32.html](esp32.html) она отправляет снимок на `POST /api/recognize`
с `X-API-Key`. AKS возвращает результат `match`, имя сотрудника и `log_id`.
После подтверждения плата принимает новый код GM67 и отправляет
`log_id` + `cargo_barcode` на `POST /api/log_cargo`.

В этом варианте запуск `app.py` на ноутбуке не требуется. Вызовы
`/api/device/trigger`, `/api/esp/heartbeat` и Device Registry отключены:
в центральном HTML эти API не определены. Проверка запускается кнопкой
на устройстве. Прежняя кнопка проверки на локальном сайте здесь не управляет платой.

Запись груза не повторяется автоматически после потерянного ответа:
центральный API не описывает гарантию защиты от повторов. При ошибке
платы оператор должен проверить, сохранилась ли запись на AKS.

## Сборка и загрузка

Для текущей одной ESP32-S3:

```powershell
cd firmware
pio run -e esp32s3cam_baku
pio run -e esp32s3cam_baku -t upload --upload-port COM9
pio device monitor -e esp32s3cam_baku -p COM9 -b 115200 --rts 0 --dtr 0
```

Для Товуза замените `esp32s3cam_baku` на `esp32s3cam_tovuz` во всех командах.
Перед загрузкой закройте действующий монитор COM9. Замените порт, если
после переподключения он изменился. Сборка сама по себе не меняет программу
на плате: для новых сетевых параметров необходима загрузка.

Ожидаемые строки после загрузки:

```text
[eth] режим: прямой AKS, API: https://aks.customs.gov.az:443/api
[eth] MAC W5500: 02:47:41:54:45:01
[eth] статический адрес 172.16.5.193
[eth] маска 255.255.0.0, шлюз 172.16.0.1, DNS 192.168.250.248
[eth] соединение https://aks.customs.gov.az:443, IP=...
[cp] сервер отвечает: хост aks.customs.gov.az:443 доступен (TLS OK; авторизация ещё не проверена)
```

TLS OK подтверждает TLS-соединение. Ключ и whitelist проверяются
при запросе распознавания: 401 означает ошибку ключа, 403 — отказ по IP.
В прямой схеме в whitelist AKS требуется разрешить источник запросов платы
`172.16.5.193` для Баку или `172.20.204.193` для Товуза
(либо адрес после NAT, если общая сеть его применяет).

Если DNS не разрешает домен, проверьте `ETH_DNS`. Если TCP/TLS не проходит,
администратор должен проверить маршрут и сетевые правила для
`IP выбранной площадки → aks.customs.gov.az:443`. Ноутбук может выбрать
Wi-Fi для своего теста вместо Ethernet; его результат не доказывает
доступность или недоступность маршрута самой ESP32.

Парсер HTTP используется также для расшифрованного TLS-потока. Вызов
`ESP_SSLClient::flush()` перед чтением убран: он очищает полученные данные
и может удалить быстрый ответ AKS. Ошибки 301/401/403 сохраняются; автоматического
перехода на HTTP или на другой сервер нет.

На проверке 07.10.2026 Ethernet ноутбука был отключён, домен через текущую
Wi-Fi-сеть не разрешался. Проверка из сети самой ESP32 после загрузки прошивки
остаётся обязательной; сборка не подтверждает сетевую доступность AKS.

Проверки кода 07.10.2026: обе сборки `esp32s3cam` и
`esp32s3cam_laptop` успешны; 78 серверных тестов прошли (ответы API
подменяются, реальные фото и грузы в AKS не отправлялись); 59 проверок
парсера HTTP прошли. Образ HTTPS занимает 514720 байт; он находится
в `firmware/.pio/build/esp32s3cam/firmware.bin`. На плату в рамках этой
проверки образ не загружался.

## Возврат к локальному стенду

Профиль `esp32s3cam_laptop` задаёт `ETH_DIRECT_AKS=0`:
сервер `172.16.6.51:8000`, маска `/24`, прежний шлюз и Device Registry.
Используйте его только в старой схеме прямого кабеля к ноутбуку.
Остальные аппаратные профили и двухплатный вариант сохранены.

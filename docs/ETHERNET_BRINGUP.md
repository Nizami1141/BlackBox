# Включение Ethernet: чек-лист от нуля до работающего поста

Порядок здесь не случайный. Каждый шаг проверяется отдельно и даёт
однозначный ответ «прошёл / не прошёл», прежде чем начинается следующий.
Если пропустить и паять всё сразу, потом придётся гадать, что именно
не работает: провод, адрес, ключ или прошивка.

Конфигурация в проекте **уже переключена на Ethernet**. Ниже — то, что
осталось сделать руками.

---

## 0. Питание — сделать ДО всего остального

Это не формальность и не «на всякий случай». Посчитаем, сколько ест пост:

| Потребитель | Ток |
|---|---|
| GM67 сканер | ~180 мА, круглосуточно (сам не засыпает) |
| W5500 | ~130 мА, в пике до 150 |
| OV5640 | ~100 мА, пока идёт XCLK |
| ESP32-S3 | 40–80 мА |
| Подсветка LCD | ~25 мА |
| **Итого** | **~500 мА** |

Порт USB ноутбука даёт 500 мА. То есть пост с W5500 упирается ровно
в предел, а в момент отправки кадра — переходит его.

Проявится это **не отказом Ethernet**, а случайными перезагрузками платы
посреди отправки кадра. Выглядит как «плата глючит», ищется долго,
а причина простая.

**Что сделать:**

* отдельный блок питания 5 В / 2 А на шину питания макетки;
* земля блока и земля платы соединены (общий GND — обязательно);
* электролит 100–470 мкФ поближе к W5500;
* W5500 питать **5 вольтами** на вход модуля, у него свой LDO 1117.
  От вывода 3.3 В платы ESP32 его питать нельзя — там свой регулятор
  с небольшим запасом, и просадка даст те же перезагрузки.

### Если отдельного БП пока нет

Таблица выше — сумма «если бы всё работало одновременно». В прошивке это
не так: `POWER_MODE 1` разносит потребителей по времени, и пики **не
складываются**. Последовательность в `checkpoint.cpp` устроена так:

| Фаза проверки | Кто ест | Итого |
|---|---|---|
| покой | W5500 130, экран 25, CPU 80 МГц ~35, камера и сканер спят | ~200 мА |
| съёмка кадра | + камера 100, CPU 240 МГц | ~355 мА |
| отправка кадра | камера уже уснула, W5500 в пике | ~285 мА |
| ожидание штрихкода | + сканер 180, CPU снова 80 МГц | ~380 мА |

Камера и сканер **никогда не включены одновременно** — луч зажигается
только после того, как кадр уже отправлен, а камера усыплена. Поэтому
реальный максимум около 380 мА, а не 500.

То есть шанс уложиться в питание от USB есть. Что для этого сделать,
по убыванию эффекта и все бесплатно:

1. **Порт USB 3.0** (синий язычок внутри разъёма) вместо USB 2.0. По
   стандарту это 900 мА против 500 — почти вдвое больше запаса, и это
   самая крупная бесплатная прибавка из возможных.
2. **Короткий и толстый USB-кабель.** Тонкий метровый кабель на 400 мА
   теряет заметную долю вольта, и до платы доезжает уже не 5 В. Симптом
   ровно тот же, что у слабого БП.
3. **Никаких USB-хабов и удлинителей.** Хаб без своего питания делит те же
   500 мА на все порты сразу.
4. **Электролит 100–470 мкФ** между 5 В и GND у W5500, если найдётся хоть
   какой-нибудь — его можно выпаять из любой старой платы. Он не добавляет
   тока, но гасит именно короткий бросок, на котором чип и срывается.

Как понять, что не уложился: смотреть в лог строку
`[boot] причина прошлого сброса`. Если там **ПРОСАДКА ПИТАНИЯ (brownout)** —
вопрос закрыт, дело в питании, и дальше искать в программе нечего.
Если там `подано питание` или `внешний сброс` — питание ни при чём.

## 1. Проводка W5500

Слот SD-карты должен быть пуст — эти пины общие, две микросхемы на одной
шине SPI будут мешать друг другу.

| W5500 | ESP32-S3 |
|---|---|
| SCK | GPIO 39 |
| SO (выход модуля) | GPIO 40 (MISO) |
| SI (вход модуля) | GPIO 38 (MOSI) |
| SCS | GPIO 41 |
| RST | GPIO 42 |
| INT | не подключать |
| 5V | 5 В от отдельного БП |
| GND | общая земля |

**Самая частая ошибка — перепутать SI и SO.** Подписи на модуле означают
вход и выход *модуля*: `SI` идёт на MOSI платы, `SO` — на MISO. Если
соединить «одноимённо», плата скажет «W5500 не найден на шине SPI».

**Проверка шага:** воткнуть патч-корд в RJ45. Светодиоды в разъёме должны
загореться **сразу, ещё до прошивки** — линк поднимает сама микросхема.
Не горят — дело в кабеле, питании модуля или в самом модуле, и дальше
идти бессмысленно.

## 2. Адрес на ноутбуке

Кабель идёт напрямую плата ↔ ноутбук, роутера нет. Значит нет и DHCP —
адрес выдавать некому, поэтому адреса заданы руками с обеих сторон:

| | Адрес | Маска | Шлюз |
|---|---|---|---|
| ESP32 + W5500 | 172.16.6.52 | 255.255.255.0 | — (уже в `config.h`) |
| ноутбук | 172.16.6.51 | 255.255.255.0 | **оставить пустым** |

```
Параметры → Сеть и Интернет → Ethernet → свойства адаптера
  → IP версии 4 (TCP/IPv4) → Свойства → Использовать следующий IP-адрес
```

**Шлюз оставить пустым.** Прописанный несуществующий шлюз Windows считает
основным и уводит в него весь трафик — ноутбук потеряет интернет через
Wi-Fi, а пост при этом работать не начнёт.

**Проверка шага:** после прошивки платы (шаг 4) команда `ping 172.16.6.52`
должна отвечать. До прошивки отвечать нечему — W5500 сам по себе на пинг
не отвечает, стек живёт в прошивке.

## 3. Сервер

```powershell
cd server
python app.py --check
```

Должно быть примерно так:

```
Конфигурация в порядке.
  бэкенд лиц : insightface (dim=512)
  порог      : 0.45
  сотрудников: 3
  управляемые: SIM-01[fake]
  автономные : GATE-01[http]   (ходят сами, кнопка «Проверить» на сайте им не нужна)
```

`GATE-01` в строке **автономные** — то, что нужно. Если он оказался
в «управляемых», значит в `config.yaml` у него остался `link.type: ble`.

Затем поднять по-настоящему:

```powershell
python app.py --open
```

**Брандмауэр Windows** при первом запуске спросит, разрешить ли Python
принимать соединения — разрешить **для частной сети**. Если случайно
запретили, второй раз он не спросит, и пост будет получать «сервер не
отвечает» при живом кабеле. Разрешить задним числом (PowerShell от
администратора):

```powershell
New-NetFirewallRule -DisplayName "Checkpoint 8000" -Direction Inbound `
                    -Protocol TCP -LocalPort 8000 -Action Allow -Profile Private
```

**Проверка шага:** с самого ноутбука открыть `http://172.16.6.51:8000/selftest`
— именно по этому адресу, а не по `127.0.0.1`. Ответ в виде JSON означает,
что сервер слушает тот интерфейс, в который воткнут пост.

## 4. Прошивка

```powershell
cd firmware
pio run -t upload
pio device monitor
```

В логе, сверху вниз:

```
=== Пост "GATE-01": автономный режим, связь по Ethernet ===
[boot] PSRAM: найдена, размер 8388608 байт
[boot] причина прошлого сброса: подано питание
[pwr]  режим 1: покой 80 МГц, работа 240 МГц
[boot] экран найден на адресе 0x27 (SDA=47, SCL=21)
[boot] кнопка на GPIO 14 (второй вывод на GND)
[boot] сканер ответил на команды — связь по UART в обе стороны есть
[gm67] сканер усыплён
[eth]  поднимаю W5500 (SCK=39 MISO=40 MOSI=38 CS=41 RST=42)...
[eth]  статический адрес 172.16.6.52
[cp]   сервер отвечает: сотрудников в базе: 3, модель insightface
[ok]   загрузка завершена, процессор на 80 МГц
```

**Главная строка — `[cp] сервер отвечает`.** Она означает, что дошло
всё: кабель, адреса, брандмауэр и ключ устройства. Если она есть,
Ethernet работает, и остаётся только сам сценарий.

## Если не работает — диагностика снизу вверх

Идти строго по порядку: каждая следующая проверка имеет смысл, только
если предыдущая прошла.

| Что в логе | Где искать |
|---|---|
| `Микросхема W5500 не найдена на шине SPI` | Проводка. Первым делом — не перепутаны ли SI/SO. Потом SCS на GPIO 41 и 5 В на модуле. |
| `Микросхема есть, но кабель не подключён` | Светодиоды в RJ45 не горят — кабель или сам модуль. |
| `сервер не отвечает` при живом линке | Три подозреваемых: не запущен `app.py`; адрес ноутбука не 172.16.6.51; брандмауэр. Проверяются `ping 172.16.6.52` и открытием `/selftest` по адресу 172.16.6.51. |
| `HTTP 401` | `ETH_API_KEY` не совпадает с `aks_api.api_key` в `server/config.yaml`. |
| `HTTP 403` | Адрес ESP32/W5500 отсутствует в `aks_api.ip_devices`; для стенда нужен `172.16.6.52: GATE-01`. |
| Случайные перезагрузки при отправке кадра | Смотреть строку `[boot] причина прошлого сброса`. `ПРОСАДКА ПИТАНИЯ (brownout)` — это шаг 0, и гадать больше не о чем. `АВАРИЯ в программе` — питание ни при чём, ищите backtrace. |
| Кадр уходит, но всегда «лицо не найдено» | Частота процессора менялась при включённой камере, XCLK уехал. Временно `POWER_MODE 0`: если заработало — дело в порядке вызовов в `checkpoint.cpp`. |
| Луч горит, штрихкод не читается | Поднести код в первые секунды. Если поднесли позже и не считалось — смотреть перевзвод сканера в `waitBarcode()`, `GM67_REARM_MS`. |

## Дальше: роутер

Меняется ровно две строки в `firmware/include/config.h`:

```c
#define ETH_USE_STATIC   0        // роутер раздаст адрес сам
#define ETH_SERVER_HOST  "..."    // адрес, который роутер выдал ноутбуку
```

Адрес ноутбука — `ipconfig`, строка «IPv4-адрес» того адаптера, которым
ноутбук воткнут в роутер.

Одна оговорка: выданный роутером адрес ноутбука может измениться после
перезагрузки, и тогда пост будет стучаться в пустоту. Либо закрепить адрес
за ноутбуком в настройках роутера (DHCP reservation по MAC), либо задать
ноутбуку статический адрес вне пула DHCP.

Если постов станет несколько — у каждого должны быть **свои**
`CHECKPOINT_DEVICE_ID`, `ETH_API_KEY`, `ETH_MAC`, свой IP и своя запись
в `devices:` серверного `config.yaml`. Одинаковый MAC у двух плат в одной
сети даёт плавающие обрывы, которые выглядят как что угодно, кроме
своей настоящей причины.
